# T3 · SQLite: DDL, reglas de integridad, 8 proveedores y budgets — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Traducir el ER (12 tablas, 12 reglas de integridad) a DDL SQLite ejecutable con CHECKs, FKs, índices, seed de 8 proveedores + policy v1 + 6 budgets + 4 fx_rates + 6 categories, y un módulo de acceso inyectable (`loadDb`/`getDb`/`closeDb`).

**Architecture:** Tres módulos en `api/src/db/`: `schema.ts` (DDL como template string + `applySchema`), `seed.ts` (`seed(db)` con `INSERT OR IGNORE` + verificación de conteo), `index.ts` (`loadDb`/`getDb`/`closeDb`). Los IDs son TEXT con UUID v4 (`crypto.randomUUID()`). Las tablas de seed usan claves naturales como PK. better-sqlite3 (ya en deps, prebuilds para Alpine musl).

**Tech Stack:** TypeScript 5.9, Node 22.23.3, better-sqlite3 13, `node:test` vía tsx.

**Spec:** `docs/superpowers/specs/2026-10-17-t3-sqlite-design.md` — el plan implementa ese spec; los dos viajan juntos.

## Global Constraints

- Todo corre dentro del contenedor. En el host `just` no está instalado: usar `bash ./scripts/compose.sh <args>`. El cwd de `compose exec` es `/app`.
- Imports relativos llevan extensión `.js` (`module: NodeNext`).
- **El script `test` de `api/package.json` es una lista explícita y hay que editarla a mano** para cada `.test.ts` nuevo.
- Prettier: 100 columnas, comillas dobles, semicolons. `just check` no corre Prettier.
- Commits: Conventional Commits, mensajes en inglés, un commit = un cambio lógico.
- `PRAGMA foreign_keys = ON` en cada conexión. better-sqlite3 no lo activa por defecto.
- Los enums del DDL deben coincidir exactamente con los de T2: `PAGAR | FRENAR | ESCALAR`, los diez `reason_code`, los siete estados de factura, etc. Sin tilde.
- `crypto.randomUUID()` está disponible en Node 22 sin imports.
- better-sqlite3 es síncrono: no hay `await` en ninguna operación de DB.

## Review Focus

Cinco formas de falla que el spec implica y que ningún test del camino feliz toca.

1. **`PRAGMA foreign_keys` no se activa.** Sin él, las FKs son decorativas y un insert con vendor_id inexistente pasa. Mitigación: `instance.pragma("foreign_keys = ON")` en `loadDb`, verificado con un test que inserta una FK inválida y espera error.
2. **`CREATE TABLE IF NOT EXISTS` no altera tablas existentes.** Si el schema cambia entre versiones, la base vieja no se actualiza. Para MVP se borra y recrea. Mitigación: documentado en el README y en el spec. El test de schema verifica que las tablas tienen las columnas esperadas (catch de drift).
3. **Seed que falla silenciosamente.** `INSERT OR IGNORE` ignora errores de constraint. Mitigación: verificación de conteo después del seed; si no son 8/1/6/4, lanza.
4. **`loadDb` llamado dos veces.** El singleton debe ser idempotente (retornar la misma instancia). Mitigación: guard `if (db) return db`.
5. **Tests que no llaman `closeDb()`.** Si un test no cierra la base, el siguiente recibe la instancia cacheada y los datos se pisan. Mitigación: `afterEach`/`after` en cada test que use `loadDb`.

```ts
import Database from "better-sqlite3";

import { applySchema } from "./schema.js";
import { seed } from "./seed.js";

let db: Database.Database | null = null;

export function loadDb(path: string): Database.Database {
  if (db) return db;
  const instance = new Database(path);
  instance.pragma("foreign_keys = ON");
  applySchema(instance);
  seed(instance);
  db = instance;
  return db;
}

export function getDb(): Database.Database {
  if (!db) throw new Error("DB no inicializada: llamar loadDb(path) primero");
  return db;
}

export function closeDb(): void {
  if (db) {
    db.close();
    db = null;
  }
}
```
